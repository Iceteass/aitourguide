## 공통 설계 제약

- 공통 앱은 정적 HTML/JS/CSS이며 설치 의존성·서버 API가 없다. v1.2 로더는 catalog→pack→POI를 상대경로로 읽고 inline 지도/TTS/사진 함수와 연결한다.
- `travel-packs/{country_code}/{city_id}/{destination_slug}/` 및 기존 팩 경로·ID를 유지한다. 국가·도시 JSON을 별도로 복제하지 않는다.
- catalog의 `path`·`cover`는 앱 기준, pack의 참조는 팩 기준, POI의 참조는 spot 기준이다. 제작 단계 데이터는 공개 런타임 catalog와 분리한다.
- 앱 버전, `pack_version`, `schema_version`은 서로 다른 계약이다. 도구·문서·CI만 바꿀 때 앱 버전을 올리지 않는다. 스키마 변경 필요성이 생기면 별도 호환성 검토 후 결정한다.
- 기존 여행팩·레거시 캐시, 개인 사진 DB의 숫자 키 및 `pack_id:poi_id` 키, 사용자 설정을 보존한다. 런타임 자산 이동·삭제·캐시/DB 마이그레이션은 별도 승인 대상으로 분리한다.
- 아래 PR 2~4의 파일명·CLI 구성은 후속 설계 제안이다. 다음 단계에서 실제 콘텐츠 지침과 사용자 요구를 재확인하여 확정하며 이번 PR에 미구현 도구를 추가하지 않는다.

## PR 1 — 앱 버전 표시 및 관리 (main 병합 완료)

**목표:** 기존 첫 화면의 배경·제목·터치 안내를 유지하고 안내 아래 `App v1.2.3`을 작게 표시한다. 팩 1.2.0과 스키마 1.0.0은 그대로 둔다.

**선택한 구현:** 정적 `app/version.js`를 HTML과 classic SW가 함께 로드한다. 앱은 이 값으로 표시와 문서 제목을 만들고 SW는 셸 캐시 이름을 만든다. 버전 JSON을 별도로 fetch하는 방식은 초기 비동기·오프라인 실패 경로가 생기므로 채택하지 않았다. 빌드 시 주입 방식은 현재 없는 빌드 도구를 추가해야 하므로 사용하지 않았다.

**작업 순서 및 완료 조건:**

1. 기존 버전 소스/표시가 없어서 실패하는 검사 작성 및 실행.
2. 단일 버전 소스, 작은 표시, 버전 기반 셸 갱신과 버전 파일 precache 구현. SW 등록은 import HTTP 캐시를 우회하도록 설정.
3. 기존의 고정 셸명 문자열 검사를 실제 worker 설치·활성화 동작 검사로 대체하고 새 검사를 CI에 연결.
4. 실제 v1.2.2를 설치하여 팩·사진·설정을 저장한 뒤 같은 origin/경로에서 새 worker로 갱신. 셸 교체 및 사용자 자료의 바이트 단위 보존을 확인.
5. 오프라인 첫 화면 버전, 터치·키보드 진입, 다운로드·지도·상세, 신규 설치를 검사하고 버전 관리 지침 작성.
6. 커밋/push/PR 준비 후 결과를 보고하고 멈춤.

**위험:** 혼합된 구/신 셸, 버전 파일 캐시 누락, 잘못된 캐시 정리, 작은 화면의 텍스트 겹침. 설치 실패 시 구 셸 유지, 실제 업그레이드 및 오프라인 브라우저 검사로 확인한다. 이미 열린 구 탭은 새로고침 전 기존 코드를 계속 실행할 수 있으며 문서에 안내한다.

## PR 2 — Creator 및 엄격 Validator (PR 1 병합 후)

**경계:** ChatGPT 제작 MD는 추천·역사 해설·출처 초안을 만든다. Codex 도구는 승인된 입력의 파일 조립·상태 저장·검증을 담당한다. 지침 MD가 미제공이면 그 사실을 표시하고 사실·권리·승인을 만들어내지 않는다.

**제안 구성:** `authoring/creator/`, 공유 `authoring/lib/`, `authoring/schemas/`에 제작 UI/CLI와 조립·검증 로직을 둔다. 기존 `validate_pack.mjs` 명령 호환성을 유지하고 공통 검증 함수가 구조화 리포트를 반환하게 확장한다. 라이브러리/ZIP 의존성 필요 여부는 단계 시작 시 결정하고 고정 버전·lockfile을 사용한다.

**제작 계약:**

- 국가 코드·도시 ID·여행지 slug/이름, 추천 spot N개, 채택/거절/수정 및 운영자 승인 결과를 입력받는다. 승인 대상과 결과를 추적한다.
- 재개 가능한 초안 문서에 원본 입력·승인·자산 연결·제작 단계·포맷 버전을 보존한다. 공개 pack의 스키마를 초안 상태 저장용으로 확장하지 않는다.
- `pack.json`, `spots/<slug>/poi.json`, `narration.md`, 별도 지도 이미지·`route/points.json`을 조립한다. 경로/순서 데이터가 추가로 필요하면 현재 런타임에서 소비하는 필드와 도구 전용 필드를 구분한다.
- 미리보기에서 지도·좌표·순서·모든 이미지·전체 원고·출처/권리/미완료 표시를 확인한다. 실제 콘텐츠가 없으면 검수 대기 상태이며 publish 불가다.
- 프로젝트 저장/불러오기·이어 만들기, 안전한 ZIP 출력, spot별 MP3 제작용 원고 출력. ZIP 경로 이탈·중복 entry·symlink 및 과도한 압축 해제를 방지한다.

**Validator 계약:**

- `draft`(MP3 없음 허용, 미완료는 WARN)와 `publish`(필수 오디오·권리/승인·전체 파일 요구) 모드를 명시적으로 구분한다.
- JSON 스키마/타입/필수 필드, 표준 경로·경로 이탈, catalog/pack/POI ID·국가·도시·버전 연결, 중복 ID, spot 수·순서·폴더 일치를 검사한다.
- 지도·표지·이미지·원고·오디오 파일 참조와 `files` 포함·크기·SHA-256, 유한 좌표의 [0,1] 범위 및 route/spot 대응·순서·단절/중복을 검사한다. 기록되지 않은 해시 처리와 기존 팩의 호환 정책은 명시한다.
- PASS/WARN/FAIL 항목, 파일·필드·원인과 요약을 JSON 및 사람이 읽는 보고서로 출력한다. FAIL은 비정상 종료하며 publish 필수 요건을 WARN으로 낮추지 않는다.

**완료 조건/시험:** 임시 디렉터리에 실제 신규 샘플을 생성하고 중간 저장→재개→ZIP→재입력 및 원고 출력 일치를 확인한다. 실재하지 않는 역사를 승인된 콘텐츠로 공개하지 않는다. 정상 팩·기존 팩을 통과시키고 ID/경로/파일 누락/해시/좌표/MP3가 손상된 입력을 각각 실패시킨다. 시험용 팩은 라이브 catalog에 등록하지 않는다.

**호환성 위험:** 엄격 검증 때문에 기존 합법적인 팩이 차단되거나 초안이 공개될 수 있다. 기존 팩을 기준 fixture로 고정하고 모드별 기대 결과를 명시한다. 스키마 1.0.0의 누락 해시 등 실제 관행과 새 게시 정책은 혼동하지 않는다.

## PR 3 — Publisher 및 전체 catalog CI (PR 2 병합 후)

**제안 구성:** `authoring/publisher/`가 Creator 프로젝트/ZIP을 안전하게 입력받고 PR 2의 검증 라이브러리를 호출한다. 콘텐츠 생성·TTS 호출·공개 배포는 자동으로 하지 않는다.

**운영 흐름:** 가져오기 → draft 검증 → 지도/이미지/원고 전체 미리보기 → 외부 TTS가 만든 MP3의 spot/언어별 명시적 연결 → 오디오 manifest와 pack/POI/files의 크기·해시 갱신 → publish 검증 → catalog 변경안과 파일 diff 생성 → 운영자 승인. 파일이 바뀌면 승인도 무효화하고 다시 검증한다. 검증 실패·미승인·매핑 누락이면 게시 준비 출력/등록을 차단한다. 오디오 manifest가 도구 자료인지 런타임 자료인지 분리하며 실제 재생 경로는 기존 POI 계약을 유지한다.

**CI:** 기존 고정 경로 명령을 보존하되 전체 catalog 순회 엔트리포인트를 추가한다. 등록된 모든 팩을 같은 Validator로 검사하고 전역 중복 pack ID·누락 pack/자산·메타데이터 불일치를 실패시킨다. PR 및 main의 관련 변경에 실행하고 기존 앱 회귀 검사를 계속 실행한다. 안전한 shell 인자 전달과 FAIL 종료 상태 전달을 보장한다.

**완료 조건/시험:** 공개 catalog를 늘리지 않고 임시 catalog와 두 개 이상의 생성 시험 팩으로 정상 전체 순회, 중복 ID·손상 파일에 대한 CI 엔트리포인트 비정상 종료를 검증한다. 승인 전/후 및 승인 후 파일 변경 시 게시 차단을 확인한다. 기존 팩의 해시·오프라인 기능도 재검증한다.

**호환성 위험:** 임의 MP3 오연결, 잘못된 manifest 갱신, 검증 경고 무시, 무승인 catalog 변경. 실제 파일 해시를 승인 대상에 결합하고 시험 팩과 공개 콘텐츠를 분리한다.

## PR 4 — 공통 자산 및 기존 앱 검증 (PR 2/3보다 선행)

이번 단계에서는 manifest 기본 이미지·fallback·오프라인 셸, 구 경로 사본 보존, 기존 팩 검증과 연계 문서를 구현한다. Creator→Publisher 전체 흐름의 완료 검증은 별도 PR 2/3 통합 뒤로 남긴다. 공통 앱과 제작 도구·여행팩의 경계를 다시 조사하고 모든 신규 팩의 표준 경로를 확인한다. 루트 MP3·지도·이미지·v1.1 파일을 동적 참조·초기 DOM·fallback·캐시·테스트·구 클라이언트 관점에서 재검증한다. 사용 파일은 유지한다. 무참조·중복이어도 사용자 캐시/외부 URL 영향을 확정하지 못하면 삭제하지 않고 근거와 남은 항목을 기록한다.

**완료 조건:** 기존 기능을 유지하며 Creator→Validator→Publisher→catalog 준비 과정을 실제 시험한다. README와 제작·검증·게시·버전 가이드를 실행 가능한 명령으로 갱신한다. 불필요한 중복, 보존 사유, 미정리·미검증 항목을 명확히 보고한다. 제거/이동이 필요하면 영향·대체 경로·기존 설치 시험 및 사용자 승인을 먼저 확보한다.

## 각 PR의 검증 게이트

기존/신규 Node 테스트 전체, JS 문법, JSON/manifest 파싱, 여행팩 참조·해시, Actions YAML/실행 대상 경로, 변경 파일·기존 데이터 영향 분석을 수행한다. 가능한 환경에서 Chromium 첫 화면·다운로드·지도·오프라인 재진입을 실행한다. 브라우저 시험의 비동기 팩 로딩은 완료를 기다린다.

로컬 검사와 원격 Actions, Pages 배포, 실기기 음성 성공은 별개다. 미실행 항목은 미검증으로 보고한다. iPhone/Android 음성·TTS·잠금 화면, 콘텐츠 사실/권리 검수는 별도 확인한다. 이번 계획만으로 후속 기능이 구현·승인·게시되었다고 간주하지 않는다.
